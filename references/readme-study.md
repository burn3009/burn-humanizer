## 对旧 README 的诊断

旧版先写“有分寸的拟人化”，接着说“抓住值得讲的细节”。这些话表达了愿望，却没有告诉第一次进入仓库的人，下载到的是程序、服务还是给模型读取的规则。

“它关心什么”一节继续解释项目的态度。“它保留事实、作者声音和指定风格”又把规则想达到的效果写成了能力承诺。句子都通顺，但读者仍未看到实际改稿。

三个调用示例都是要求模型做事，没有展示处理前后发生了什么。因此，用法看似给了例子，功能仍然是抽象的。“由 burn 维护”值得交代，放在来源处就够了，不需要在首屏作为卖点强调。

问题不只是字数。这份 README 中的态度陈述占用了本可以解释工具和示范改稿的位置。即使把它再缩短一半，也可能只剩下更密集的口号。

## 样本支持什么

工具文档中的具体对象很重要。write-good 和 proselint 都让读者看到输入如何对应到输出；中文排版指北让读者直接比较字符与空格。对本项目，补一组原句与改句，比再声明一次“自然”更有用。

篇幅取决于文档职责。write-good 需要解释 API 和扩展，技术写作规范的首页只是入口。它们的长度不能互相作为合格线。本项目也不应把“读者注意力有限”推导成任何文稿都必须短。

玩笑与态度可以存在，但不是必要条件。中文排版指北与 write-good 的局部表达带有个性；技术写作规范的首页没有类似安排，照样能完成任务。不能从这些样本推导出“每篇都要找一个趣味点”。

明确的判断也不等于说教。排版规则可以直说正确与错误，同时把可争议的选择标出来。本项目要避免的是把审美偏好包装成普遍法则，而不是把所有判断软化。

proselint 是有必要保留的反例：历史文档也会使用宏大开场、名家名单和宣传语。因此，不能用这些表面特征来断定一篇文稿是不是 AI 写的。它们是否适合当前 README，应单独讨论。

## 本次修改

README 改为先交代规则文件的用途，给一个通知改写例子，再说明安装和调用。删除标语及大段自我评价，保留来源、许可和未做盲评的事实。例子是本项目为说明编辑取舍编写的，不是历史样本的引文，也不是模型效果实验。

技能增加按文体判断的要求，并把这份对照记录列为 README 任务的参考。没有据此设定字数上限、禁用列表或强制幽默。

这次只分析了文档内容与 Markdown 组织，未评估样本当年的网页渲染、品牌配色或图像风格。不能把 GitHub 当前统一的页面外观当作作者当年的视觉设计证据。
